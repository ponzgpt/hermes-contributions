Chapter 01

What Hermes Agent actually is

An agent receives a goal, reasons about the next step, calls tools when needed and keeps going until it can return a result. The model is only one part of the system.

Model

Produces the next decision or response.

Tools

Let Hermes inspect or affect the world around it.

Context

Contains instructions, history, files and tool results.

Runtime

Determines where commands actually execute: local, Docker, SSH or cloud.

Chapter 02

The first useful setup

Start with one provider and one normal conversation. Do not add a gateway, cron, MCP servers and five models before the basic loop works.

curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
hermes setup --portal

Chapter 03

Price points for a sane model setup

Hermes has a main model for the visible agent loop and separate auxiliary slots for side jobs such as compression, vision, web extraction, approvals and titles. Every auxiliary slot defaults to the main model unless you override it. That default is convenient and can become expensive.

These are practical starting combinations, not permanent rankings. Prices are a dated snapshot from the Nous Portal catalogue, shown per 1M input / output tokens in USD. Portal discounts and model availability change: check the live catalogue before spending money.

Do not read “cheap auxiliary” as “always good enough”. Compression and web extraction can lose important details. Test a proposed auxiliary model on your own workload before trusting it.

What to configure first

model:
  provider: "nous"
  default: "anthropic/claude-sonnet-4.6"

auxiliary:
  compression:
    model: "google/gemini-3.1-flash-lite-preview"
  web_extract:
    model: "google/gemini-3.1-flash-lite-preview"
  vision:
    model: "google/gemini-3.1-flash-lite-preview"

Treat provider and model IDs above as examples to verify in hermes model or the live catalogue. Prefer the interactive setup over hand-editing configuration while learning.

Chapter 04

Tools are powers, not decoration.

Before asking Hermes to change something, identify the tool that can make the change and the boundary around it. Local execution has your user permissions. Docker gives you a different boundary. SSH moves the effect to another machine.

  1. Ask for an observation first.
  2. Request a plan before a destructive action.
  3. Use the narrowest toolset that completes the task.
  4. Read the result back. “The command ran” is not the same as “the job worked”.

Chapter 05

Memory and skills

Memory stores durable facts about the user and environment. Skills store reusable procedures. They solve different problems. If a lesson is “Javier prefers concise Spanish responses”, it is memory. If it is “how to publish a verified static site”, it is a skill.

Memory

Who you are, what stays true and how you work.

Skills

How to perform a recurring job, with checks and failure paths.

Context files

Rules that should shape work in a project or directory.

Chapter 06

Operate without guessing.

When something breaks, stop adding features. Check provider authentication, model name, logs, working directory, tool availability and the last successful step. Keep secrets in the secret store or .env; keep normal settings in config.yaml.

Useful recovery questions:

  • Did the model answer at all?
  • Did Hermes call the expected tool?
  • Did the tool run in the place I thought it did?
  • Can I reproduce the result with a smaller task?
